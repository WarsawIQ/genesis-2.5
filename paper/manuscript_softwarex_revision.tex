\begin{abstract}
%% about 100 words (R10). One speed number, one correctness number, one limit.
GENESIS is a long-established compartmental neural simulator. GENESIS~2.5 adds
optional CUDA and OpenCL backends to its \texttt{hsolve} solver, including a GPU
Hines elimination for populations of dendritic trees, without changes to existing
models, scripts or MPI workflows. On a population of 160\,000 compartments the
accelerator runs \claim{e2_max_e2e_a100}$\times$ faster end to end than the CPU
solver; in double precision it reproduces the CPU solver to every printed digit.
Networks that exchange spikes every step gain nothing on the GPU, and we show
why. The release also makes model construction linear and fixes two defects
in the Hines solver of GENESIS~2.4.
\end{abstract}

%% ===================================================================== 1
\item Motivation and significance
%% 550 words. R1 (relationship to GENESIS 2.4) goes here.

GENESIS~\cite{bower1998} and its MPI version PGENESIS are among the
longest-maintained compartmental simulators. Models are written as SLI scripts,
cell files and channel prototypes, often accumulated over many years, and the
compute engine is \texttt{hsolve}, an implicit Hines solver~\cite{hines1984efficient}
that compiles a model into a flat program at setup. Until this release every step of
that program ran on the CPU.

\textbf{Relationship to GENESIS~2.4.} %% R1
GENESIS~2.5 is an independently maintained derivative of GENESIS~2.4, released under
the same licence as a fork of the project's repository (\texttt{genesis-sim/genesis-2.4},
last changed in 2019). It is not an official release of the GENESIS project. The second
author has used GENESIS and PGENESIS since his doctoral work~\cite{wojcik2004lsm} and
met its maintainer, Dave Beeman, at the EU Advanced Course in Computational
Neuroscience in \'Obidos in 2001; the first author completed his PhD under the second
author's supervision in 2023. On 30 September 2026
we offered the work to the original project: the solver fixes as a pull request, and
the whole release as its next version. \pending{upstream_status}
%% Outcome by submission: reply / PR number / no reply.

\textbf{Alternatives, and what they ask of a user.} NEURON~\cite{hines1997neuron} with
its engine CoreNEURON~\cite{kumbhar2019coreneuron} and Arbor~\cite{arbor2019} run
compartmental models on GPUs and are strong choices for a new model. For an existing
GENESIS model each means re-expressing it in another description, and establishing
that the port computes the same thing is itself experimental work. For the published
network used below, it took a transcription of the channels and a comparison of spike
trains (Section~3). NEST~\cite{gewaltig2007nest} and Brian~2~\cite{stimberg2019brian} simulate
point neurons. GENESIS~2.5 offers acceleration without migration: the same scripts on
the hardware the user has.

\textbf{Contributions.}
\begin{enumerate}
\item CUDA and OpenCL backends for \texttt{hsolve}, selected at run time, in single or
      double precision, falling back to the CPU for anything they cannot compute.
\item \hte{}, a GPU Hines elimination for populations of dendritic trees.
\item Two fixes to the Hines solver of GENESIS~2.4, which with several cells under
      one solver computed wrong voltages (backward Euler) or crashed
      (Crank--Nicolson), and model construction in linear time; both apply with or
      without a GPU and are offered to the original project.
\item A comparison with NEURON, CoreNEURON and Arbor in which every arm is measured in
      one session, and a reproduction package that regenerates every number in this
      paper from raw data (Section~3).
\end{enumerate}

\item Software architecture

%% Fig. 1: architecture diagram (new; replaces the fp32/fp64 divergence figure).
\begin{figure}[!h]
\centering
\includegraphics[width=\textwidth]{figures/fig_architecture.pdf}
\caption{How a model reaches the GPU. \texttt{hsolve} compiles the model into an opcode
program at \texttt{SETUP}. A gate checks the program against what the kernels
implement; anything else stays on the CPU. Accepted models run as one of three
dispatches: per step, batched over many steps for isopotential cells
(\ccm{}), or batched for dendritic trees (\hte{}). Synaptic events are delivered by the
host every step.}
\label{fig:architecture}
\end{figure}

The backends sit behind one entry point in \texttt{hsolve}
(Fig.~\ref{fig:architecture}). The SLI interpreter, the element tree, the scheduler
and the PGENESIS MPI layer are those of GENESIS~2.4. A user selects a backend with
\texttt{chanmode} and environment variables. Nothing in a model script changes.

An accepted model runs on one of three paths. \emph{Per step}: the device updates
channels and solves each step, and the host delivers synaptic events and spikes between
steps. This is the path of any network whose cells exchange spikes. A spike emitted in
one step therefore reaches its targets in the next; the CPU solver delivers it within the
step to the cells after the sender in its loop, so with zero axonal delay the two can
differ by one step for some synapses (Section~3, correctness over a long run).
\emph{Multiloop}:
for isopotential cells without synaptic input, one launch runs $K$ steps.
\emph{Tree loop}: for populations of dendritic trees, the channel update and \hte{}
run back to back for $K$ steps. On the two batched paths the state goes to the device
once and the membrane potentials come back once per batch, so a run of $K$ steps
costs one transfer instead of $K$.

\textbf{Design decisions.} %% R2
\begin{enumerate}
\item \emph{The kernels interpret the solver's own program.} Both backends execute the
      opcode program \texttt{hsolve} already builds, so every model it accepts runs
      unchanged. GPU-native simulators generate code per mechanism instead. Interpreting
      costs divergence and a fixed setup time (Section~3), and is why existing
      models need no porting.
\item \emph{The tree solve needs no synchronisation.} The elimination program of a
      population is block-diagonal: each tree touches only its own rows. One thread per
      tree runs the CPU's elimination with no barrier, once the opcode that joins two
      trees in the CPU program is split per tree.
\item \emph{What the kernels cannot compute is refused, not approximated.} The first
      release accepted models with synaptic, spike, GHK and concentration elements and
      returned plausible wrong voltages. Such programs are now detected at
      \texttt{SETUP} and computed on the CPU.
\item \emph{The device owns the state it computes.} With synaptic input the host
      writes only the slots it owns each step. Uploading the whole state, as the first
      release did, overwrote gating variables the kernel had just updated.
\end{enumerate}

\textbf{Execution model.} %% R6
Four properties of the device code decide where it pays off.
\emph{Work imbalance.} \hte{} runs one thread per tree, so the threads of a warp wait
for the largest tree among them. A population that mixes trees of 8 and 64
compartments in every warp takes \claim{e7_inter_over_uniform}$\times$ as long per
step as uniform trees with the same total number of compartments; the same mixed trees
grouped by size take \claim{e7_block_over_uniform}$\times$ (E7). Grouping is worse,
not better: it puts all the long trees on some of the multiprocessors, which then
finish last, while interleaving spreads them across the device.
\emph{Divergence.} Compartments with different channel sets follow different opcode
streams through the interpreter, so heterogeneous cells cost more than their
compartment count suggests.
\emph{Transfers.} On the batched paths transfers are fixed per batch, not per step
(above). On the per-step path they are paid every step.
\emph{Launch overhead.} In the tree loop on the A100 the host spends
\claim{f2_host_us_per_step}\,\textmu s per step launching the two kernels, which take
\claim{f2_kernel_us_per_step}\,\textmu s (Nsight Systems, $N=10\,000$ trees); the
launches overlap the kernels, so the host is not what limits the loop. CUDA Graphs,
which replay a recorded sequence of launches, cut the host's part to
\claim{f2_host_graph_us_per_step}\,\textmu s per step and recover
\claim{e8_gain_tree_k50000_a100}\,$\pm$\,\claim{e8_gain_tree_k50000_a100_sd}\% of the
run time on the A100 and
\claim{e8_gain_tree_k50000_a40}\,$\pm$\,\claim{e8_gain_tree_k50000_a40_sd}\% on the A40
in a run of $K=50\,000$ steps (E8). In shorter runs the gain is within the noise
(\claim{e8_gain_tree_k5000_a100}\,$\pm$\,\claim{e8_gain_tree_k5000_a100_sd}\% and
\claim{e8_gain_tree_k5000_a40}\,$\pm$\,\claim{e8_gain_tree_k5000_a40_sd}\% at
$K=5000$). They change no result, so they are on by default for the tree loop. On the
spiking network they gain nothing within error
(\claim{e8_gain_spiking_a100}\,$\pm$\,\claim{e8_gain_spiking_a100_sd}\%): its
cost is the host's event delivery and the synchronisation it forces every step, not
the launches. Moving spike delivery to the device is the next step for that workload.

\item Software functionalities

\textbf{Precision.} %% R4
Single precision is the default. \texttt{GENESIS\_GPU\_PRECISION=fp64} selects double
precision at run time in the same binary, and a device without it refuses with a
message and computes on the CPU. In fp64 the GPU reproduces the CPU solver to every
printed digit on our verification models; in fp32 it agrees to
\claim{fp32_single_ap_v}\,V over one action potential. Synaptic weights and
plasticity are computed by the synapse objects on the host in double precision in every
mode. Only the resulting activation reaches the device. What double precision costs
on each card, and how the two precisions compare over a 10\,s run, are measured in
Section~3.

\textbf{Portability.} %% R7
The OpenCL backend runs the same kernels on any OpenCL~1.2 device. We test it on the
NVIDIA A40 and A100 and on the AMD Radeon~890M integrated GPU under two independent
implementations, AMD ROCm and Mesa rusticl (E9). The two differ even in what they
offer on the same chip: ROCm exposes double precision and rusticl does not, so under
rusticl a request for fp64 is refused and the model computes on the CPU. On an
integrated GPU that also drives the display, a tree dispatch above about
\pending{e9_igpu_cap_compartments} compartments trips the driver's watchdog. The
backend therefore declines the batched tree dispatch for larger models there, says so,
and runs them step by step, unless \texttt{GENESIS\_OCL\_TREE\_MAX\_NCOMPTS} says
otherwise.

\item Sample code
A model needs no change beyond the solver mode that GENESIS~2.4 already has. An
existing script that builds its solver as

{\small\begin{verbatim}
create hsolve /net/solver
setfield /net/solver path "/net/##[][TYPE=compartment]" chanmode 4
call /net/solver SETUP
\end{verbatim}}

runs on the GPU when started with the accelerated binary. Batching and precision are
chosen when the run starts, for example
\verb|GENESIS_CUDA_MULTILOOP=<K> GENESIS_GPU_PRECISION=fp64 nxgenesis -batch model.g|.
The start-up lines name the backend, the precision and the dispatch path in use, and
a model the device cannot compute is reported and run on the CPU.
\end{enumerate}

\item Correctness over a long run %% R4
%% E5, Fig. 6 (or a table if the figure budget is short).
The GPU and CPU solvers do not order spikes the same way. On the GPU a spike emitted
in one step reaches its targets in the next; the CPU solver delivers it within the step
to the cells after the sender in its loop. With this network's zero axonal delay the
two schedules differ by one step (50\,\textmu s) for some synapses, and the network is
chaotic, so it amplifies the difference. Over 10\,s of the spiking network, twice the
length of any comparison above, the GPU's spike train first departs from the CPU's
after \claim{e5_div_g64_ms}\,ms in fp64 and \claim{e5_div_g32_ms}\,ms in fp32.
The two precisions part at the same step, so the cause is the order, not rounding. The
CPU's own order matters as much: run with one solver per cell instead of one per
layer, the same network with the same seed departs from itself after
\claim{e5_div_pcell_ms}\,ms. From then on only statistics can be compared. Against
the CPU's \claim{e5_rate_cpu_hz}\,Hz, the spike count differs by
\claim{e5_count_g64_pct}\% in fp64, \claim{e5_count_g32_pct}\% in fp32 and
\claim{e5_count_pcell_pct}\% for the CPU in the other order; the KS distances
between the interspike-interval distributions are \claim{e5_ks_g64},
\claim{e5_ks_g32} and \claim{e5_ks_pcell}. Four other seeds, other draws of the
same network, fire at \claim{e5_rate_seed_min_hz}--\claim{e5_rate_seed_max_hz}\,Hz
with KS distances of \claim{e5_ks_seed_min}--\claim{e5_ks_seed_max}. Each run
repeats spike for spike on its own backend. The GPU's spike counts thus differ from the
CPU's by about as much as the CPU's differ from themselves under another update order,
its interspike intervals are closer to the CPU's than that run's are, and both
differences are far smaller than the change from one draw of the network to another.

\item Reproducing these results %% R11
Every number in this paper is a row of \path{reproduce/claims.csv}, naming the data
file, the rows and the formula it comes from and the script that measures it;
\path{make_numbers.py} computes the manuscript's values from those files, and a lint
lists any number typed by hand. \texttt{sh reproduce/run\_all.sh} measures them
again on the reader's hardware (about 15 minutes for the central claims, 95 for the
sweeps; NVIDIA GPU, CUDA 12.x). \texttt{--cpu-only} reproduces the
hardware-independent results in about two minutes on any Linux machine, and the same
path runs in a container (\texttt{docker build -t genesis25-cpu . \&\& docker run
--rm genesis25-cpu}) with nothing installed. Both run in the repository's CI on every
commit. A generated table in the README says which results need which hardware. The
comparison simulators and the reference model are built by committed recipes with
pinned versions and checksums. Rebuilding them from an empty directory reproduced the
published CoreNEURON GPU run to the spike.
\end{enumerate}

%% ===================================================================== 4
\item Impact
%% 600 words. Construction scaling (Fig. 5) and the solver fixes reach every user,
%% with or without a GPU.
Two of the release's changes reach every GENESIS user, with or without a GPU.
First, the solver fixes: in GENESIS~2.4, putting several cells under one
\texttt{hsolve} silently computed wrong voltages for every cell but one under backward
Euler, and crashed under Crank--Nicolson. The configuration is natural for networks,
so models may exist whose published results this touched. GENESIS~2.5 computes each
cell exactly as if it were alone, shown by a committed test against a single-cell
reference, and we have offered the two fixes, with the test, to the original
project. \pending{upstream_pr_status}
%% merge with the upstream_status sentence of Section 1 when the outcome is known.

Second, construction. Building a model was quadratic in its size: wall time grew as
compartments$^{\claim{e3c_before_exponent_inf03}}$, which made population-scale
models impractical regardless of compute power: a 1.7-million-compartment
population never finished building. Four scans of the element tree are now constant-
or linear-time, construction grows as
compartments$^{\claim{e3c_construction_exponent}}$, and the same population builds
in \claim{e3c_construction_1700k_s}\,s (Fig.~\ref{fig:construction}). This holds
for models built element by element, the common case. Copying a whole prototype cell
thousands of times under one parent remains quadratic; we say so rather than claim
``linear'' outright. Together with the tree kernel this moves
population studies (parameter sweeps over thousands of morphological neurons,
PGENESIS runs partitioned over MPI ranks) from a cluster queue onto the workstation
a modeller already has, in the simulator their models are written for. The practical regimes, including where the GPU does not help, are in
Table~\ref{tab:regimes}.

Beyond GENESIS, two elements of this work transfer. The refusal rule (a backend that cannot compute a model says so and computes on the
CPU, rather than approximating) is, we think, the main lesson for anyone adding an accelerator to
an existing solver; the first release approximated, and returned plausible wrong
voltages. And the reproduction mechanism (a claim map from every published number to
its raw data, regenerated into the text, checked in CI) is independent of GENESIS
and would serve any computational paper.

%% ===================================================================== 5
\item Conclusions
%% ~170 words.
GENESIS~2.5 gives a long-established simulator opt-in GPU execution without asking
its users to migrate: the same SLI scripts, cell files and MPI workflows run
unchanged. The CUDA and OpenCL kernels execute \texttt{hsolve}'s own compiled
program, in single or double precision chosen at run time. Populations of dendritic
trees gain the most, up to \claim{e2_max_e2e_a100}$\times$ end to end. Single
detailed morphologies and zero-delay spiking networks gain nothing, and the
measurements say why: too few trees to fill the device in the first case, host-side
event delivery every step in the second. The next step for that workload is spike
delivery on the device. The solver and construction fixes stand on their own and have been
offered to the original project. Every number in this paper regenerates from raw
data in the repository, the hardware-independent ones on any Linux machine or in a
container, so a reader can check what we claim before trusting it on their own
models.

\end{enumerate}
